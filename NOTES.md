# Format notes

**Target: Factorio 2.1.23** (the user's game: mac-arm64, Steam). Facts the tools and skill rely
on, with how each was established. "Game" means a headless server (free
download from factorio.com; `latest` is 2.1, `stable` is 2.0) driven over
RCON: import with `LuaItemStack.import_stack`, re-export with `export_stack`,
build with `build_blueprint` + `revive`, then read the live entities.

## Draftsman 4.0.1 vs real 2.1.22 exports

124 placeable entities were placed in a 2.1.22 server, with every writable boolean control-behaviour setting flipped and every network selection set. 119 exported; the 5 failures were the 4 rolling-stock types and the space platform hub. Of the 119, Draftsman:

- accepts 64 cleanly.
- doesn't model keys in 51. Examples: `read_ingredients`, `read_fuel` (crafting machines), `set_filter` (splitters, pumps), `set_priority_list` / `set_ignore_unlisted_targets` (turrets), `input_networks` / `output_networks` (most types), `else_outputs` (decider), `circuit_enabled` (power switch, offshore pump), `read_contents` / `read_empty_slots` (all chests), `read_charge`, `read_launched`, `circuit_read_sensor`, `circuit_close_signal`.
- crashes on car, tank, spidertron (`TypeError ... 'mode'`).
- has no entity class for `thruster`, though the name is in its data.

Samples live in `tests/fixtures/game-2.1.22/`. Not separated: which of these keys are new in 2.1 and which Draftsman lacks for 2.0 too.

Consequences for this repo:
- **Game-settings registry** (`tools/game_settings.json`, from `python -m validator.harvest`). It lists the control_behavior keys the game writes that Draftsman doesn't model: 43 settings on 22 prototype types in 2.1.22. Each setting records the entities it was seen on, because one prototype type can differ: `read_fuel` exists only on burner machines, and `set_requests` only on requester and buffer chests. Generators set these keys with `tools.settings.game_settings()`, which refuses anything outside the registry. `tests/test_validator.py` round-trips every entry on every entity it lists in the game, so CI proves each one.
- `bp check` stays quiet on registry keys. It warns on other unknown control_behavior keys (a typo, or a setting not harvested yet) and on unknown keys elsewhere. Across the 119 real 2.1.22 exports, that leaves 5 warnings, all genuine Draftsman gaps: 3 vehicle crashes, `thruster` with no class, and the asteroid collector's `result-inventory`. Unknown **names** are errors unless the game (the `data/` dump, else Draftsman's data) knows them.
- The registry only covers settings that show up when booleans and network selections are flipped. A setting that needs a chosen signal or a number to appear (the turrets' own `priority_list`, for instance) isn't in it yet.
- Draftsman may write older keys that 2.1 migrates (as with the chest) or drops. `bp gen --validate` catches the drops; migrations verified so far: logistic chest mode.
- Turret priority targets: the game exports `"priority-list": [{"index": 1, "name": ...}]` (from 1) and `"ignore-unprioritised": true`. Draftsman 4.0.1 numbers them from 0, and the game then drops the whole turret on import (`import_stack` returns -1). Its `ignore_unprioritized` key is dropped silently. Set `TargetID(index=i + 1, ...)` and the game's key through `extra_keys`. (A railgun turret with targets set by script, exported by 2.1.22; each variant validated.)

## Draftsman behaviour worth knowing

- `to_dict()` omits defaults (`direction: 0`, `copy_count_from_input: true`, network flags that are `true`). The game omits them too on re-export.
- `entities.append(e)` stores a copy. Wire by `id=` or index, not by the local object.
- Wrong footprint for `railgun-turret`: Draftsman derives 3×4 from the collision box, but the 2.1.22 prototype sets `tile_height = 5`. Placed with `tile_position`, it lands half a tile off, and the game moves it. Every other grid-placed entity matches the dump. Vehicles, rolling stock and curved/diagonal rails differ too, but they aren't placed on the tile grid.
- It resolves wire endpoints by list position, so `entity_number` must run 1..n (game exports always do). `check` enforces this.
- It doesn't check wires to missing entities (it crashes), connectors on the wrong entity kind, out-of-range connector IDs, or wire reach. `tools/check.py` covers those.

What rules out most of it is attrition per kilometre, not production. Next, in order:

1. Thruster fuel and oxidizer on board: done (`platform.build(fuel=True)`, `platform-fuel`). Collectors only catch chunks in the railgun row, and a platform standing still meets too few asteroids to start, so flights start primed and moving. From the solar system edge it needs a reserve filled before leaving (`reserve=True`: a storage tank on each line, sharing the line's fill), and then lives 8 of 8 and flies 78% as far as on fuel by script (86% at 0.4). On its own fuel the module isn't hit; at full speed it costs a flight or two in eight, which spares don't buy back.
2. Fusion power: done (`platform.build(power=2)`, `platform-power`). Two reactors, because railguns take power first and one reactor collapses where promethium is. Readied in orbit (reactors full of cells, loops of cold fluoroketone, the accumulator and railguns charged), it uses about 1.6 cells an hour at the edge and 7.7 at 0.4: cell use follows output. With its parts in the hub it rebuilds and restarts what asteroids destroy (`platform-plant`: short of power 7.0 s a flight against 21.2 without): a rebuilt reactor starts empty, so the cell belt reaches every reactor. A loop runs on as little as 50 fluoroketone and starts near 3,400, so no refill is needed yet; on a longer trip, cold fluoroketone barrels emptied in an assembling machine would refill it.
3. Losses per kilometre: `Flown.budget()` now gives what a flight used per 1,000 km beside per second, so designs at different speeds compare fairly. Ammo (`platform-ammo`): only uranium rounds hold where promethium is (piercing 5 of 8, firearm 0 of 8); at the edge piercing rounds do as well (8 of 8) on 2.3 times the magazines, and making them there takes about 59 furnaces, 12 assemblers, 7 crushers and 19 MW. 14. Space. `bp density` measures how any blueprint spends its tiles. Rows are near their own optimum; a factory's connections take 5 to 6 times the rows' area. The proposal (`docs/layout-optimizer.md`): a constructive factory layout first, measured against today's, then CP-SAT floorplanning with a grid router if the gain is still large; alongside, a `research=` option for inserter capacity on the row generators. The constructive layout is built (`factory ... layout=compact`): 32 to 44% smaller on item factories, still 2.8 to 4.6 times its rows' area (channels and the west bus), fluids still on the bus. Then a search budget (`budget=`, 40 s) and a ragged bus: 8 to 11% smaller where the widest shelf stands above a line's last tap, the rest unchanged; mirrored rows were measured not to pay (a stack needs a channel per shelf plus one, whichever way rows face). Channels are now the biggest share, 29 to 53%; the note says what's next. A CP-SAT floorplan (rows anywhere, not on shelves) was prototyped and doesn't pay: the channels are the routing the rows need, the same height either way, and its only gain would be the west bus strip, which costlier margins eat first; the numbers are in the note. Direct insertion is built (`gen cell`, from inserter rates measured machine to machine) and in the compact search: 8 of the 34 requests come out 5 to 40% smaller, every one fusing copper cable into circuits, and their channels fall from 19 to 53% of the box to 9 to 32%. It loses where one producer outpaces many consumers (gears into science: a producer reaches only its two neighbours) or where rounding consumers up rounds producers up too. A shared product now fuses into each consumer that takes a cell, a row kept for the rest: processing units and production science leave the bus (5,000 and 3,864 tiles against 8,505 and 4,784), logistic science comes out 14% smaller; a cell with consumers of two kinds isn't needed (what keeps the rest a row is what those consumers take in, not sharing). A second input belt lets advanced circuits and engine units take a cell (`gen cell ... belts=2`), but those cells lay out larger, so the search doesn't use it.
